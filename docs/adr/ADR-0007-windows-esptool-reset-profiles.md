# ADR-0007 — Совместимые с esptool профили reset в Windows

**Статус**: Accepted, 2026-08-13
**Связанные требования**: REQ-003, REQ-015, REQ-029, REQ-030

## Контекст

На CH340-плате официальный esptool 4.5.1 стабильно выполнял ROM handshake, тогда
как три попытки espflash 4.3.0 завершались по 20-секундному таймауту до начала
erase/write. Повтор одной и той же reset-последовательности не устранял различие.

## Решение

Supervisor передаёт номер ограниченной connect-попытки в same-EXE worker.
Попытка 1 воспроизводит Windows ClassicReset esptool с задержкой 50 мс, попытка 2
использует ту же последовательность с задержкой 550 мс, попытка 3 сохраняет
DefaultReset espflash как резерв совместимости. После ручной последовательности
espflash получает `NoReset` и отвечает только за sync, chip detection и stub.

Последовательность включает обновление DTR после каждого изменения RTS — это
повторяет Windows workaround pySerial/esptool. До успешного handshake mutation
не объявляется, поэтому timeout и retry остаются безопасными.

## Альтернативы

- Повторять DefaultReset espflash три раза: уже воспроизводит дефект.
- Запускать Python/esptool из приложения: нарушает portable и no-dependency
  требования.
- Требовать удержания BOOT оператором: неприемлемо для серийной прошивки.
- Полностью заменить espflash: существенно расширяет область и риск изменения.

## Последствия

- Первые две попытки соответствуют подтверждённому на проблемной CH340-плате
  поведению esptool и имеют разные аппаратные timing.
- Worker protocol получает внутренний envelope с номером попытки; публичный IPC
  не изменяется.
- HIL-08 обязателен для Windows release-кандидата.
