# Спецификация: ESP32 Flasher

**Feature branch**: `001-esp32-programmer`  
**Создано**: 2026-07-29  
**Статус**: Approved  
**Исходное описание**: Portable-утилита Windows для первичной серийной прошивки и самостоятельного обновления ESP32 клиентами.

## Пользовательские сценарии и тестирование

### US-001 — Клиент обновляет устройство

Клиент запускает один EXE без установки, выбирает конкретный application BIN с любым именем, подключает устройство и нажимает одну кнопку. Приложение читает разметку непосредственно с платы, проверяет образ и устройство, обновляет неактивный раздел, показывает прогресс, перезапускает плату и открывает UART-монитор.

**Самостоятельная проверка**: выполнить обновление одним `firmware.bin` устройства с factory-only разметкой и устройства с OTA-разметкой, убедиться в сохранении пользовательских данных и открытии UART-монитора.

**Критерии приёмки**:

1. При одном подключённом COM-устройстве порт выбирается автоматически без
   открытия порта и переключения DTR/RTS; совместимость ESP32 определяется только
   после явного запуска операции.
2. Файл не `.bin`, неверный ESP-образ или несовместимый чип блокируются до записи.
3. При OTA-разметке предыдущий образ остаётся загрузочным до успешной записи нового слота.
4. После записи пользователь видит UART-вывод с исходными границами строк; длинные строки не переносятся и доступны через горизонтальную прокрутку.

### US-002 — Оператор серийно прошивает новые платы

Оператор выбирает обычную папку PlatformIO с `bootloader.bin`, `partitions.bin`, `firmware.bin` и необязательным `boot_app0.bin`, подключает по одной плате и запускает каждый цикл кнопкой. Адреса приложения и OTA data извлекаются из `partitions.bin`; адрес загрузчика определяется по чипу. После записи и проверки приложение фиксирует результат, показывает счётчики и остаётся в мониторе до отключения платы.

**Самостоятельная проверка**: последовательно прошить не менее десяти плат одним пакетом, включая успешный цикл и цикл без UART-маркера.

**Критерии приёмки**:

1. Папка из трёх или четырёх стандартных BIN PlatformIO распознаётся напрямую и записывается по проверенной карте flash.
2. Каждый цикл запускается только оператором и относится ровно к одной плате.
3. `OK` фиксируется после flash verify и, если оператор настроил UART-маркер, после получения маркера.
4. После отключения платы приложение готово к следующему циклу не позднее чем через две секунды.
5. Для каждой платы существует отдельная строка отчёта с временем, COM, MAC, чипом, версией, длительностью и результатом.

### US-003 — Разработчик передаёт результат сборки

Разработчик передаёт обычные BIN-файлы PlatformIO без обязательной генерации манифеста. Дополнительный CLI может сформировать версионированный пакет для воспроизводимых релизов, но основной EXE не требует этого шага.

**Самостоятельная проверка**: выбрать обычную папку из трёх PlatformIO BIN и конкретный application BIN с произвольным именем; убедиться, что оба входа распознаны автоматически.

**Критерии приёмки**:

1. Для стандартного сценария не требуется создавать или редактировать JSON.
2. Карта первичной прошивки выводится до изменения flash.
3. Неоднозначный или неполный набор BIN блокируется с указанием причины.

### US-004 — Пользователь открывает UART без прошивки

Пользователь выбирает COM-порт и переходит на вкладку UART. Приложение пассивно
открывает монитор на сохранённой скорости, не запуская flash и не выполняя reset.
Монитор продолжает читать данные при переходе на вкладку «Процесс». Пользователь
может явно отключить/подключить монитор или выполнить обычный reset платы.

**Самостоятельная проверка**: открыть монитор работающей платы без выбранной
прошивки, получить непрерывный UART, отключить и повторно подключить монитор,
перезапустить плату и увидеть boot log.

**Критерии приёмки**:

1. Первый вход на UART автоматически открывает выбранный порт без flash/reset.
2. Ручное отключение не отменяется переключением вкладок; доступна явная кнопка
   «Подключить».
3. При старте flash монитор закрывается с ожиданием освобождения порта, UI
   переключается на «Процесс», а UART блокируется до завершения операции.
4. После успешного flash UART открывается автоматически; reset доступен только
   при подключённом мониторе и не переводит плату в bootloader.

### US-005 — Пользователь скачивает публичный ESP32 Flasher

Пользователь находит проект по запросам о прошивке ESP32 в Windows, открывает
англоязычную страницу, скачивает один portable EXE из GitHub Release и запускает
его без установщика. Интерфейс использует русский язык только при русском
системном locale Windows; во всех остальных случаях используется английский.

**Самостоятельная проверка**: открыть опубликованные README, GitHub Pages и
Release; скачать EXE; запустить его с `ru-RU`, `en-US` и ещё одним нерусским
locale; проверить название продукта, язык, основные метаданные и отсутствие
установщика.

**Критерии приёмки**:

1. Продукт, окно, EXE, README, Pages и release asset называются ESP32 Flasher.
2. `ru-*` включает полный русский интерфейс, любой другой или неизвестный
   locale включает полный английский интерфейс, включая ошибки и стадии.
3. Публичные README, Pages, release notes, repository description и topics
   написаны по-английски.
4. Pages содержит точное описание возможностей, FAQ, метаданные для поисковых
   систем, структурированные данные и прямую ссылку на latest release.
5. Исходный код открыт, распространяется по MIT и сохраняет attribution
   исходного проекта.

## Граничные случаи

- Подключено несколько COM-устройств.
- COM-порт занят другой программой или исчезает в процессе операции.
- Подключён неизвестный USB-UART мост.
- Папка содержит неизвестные дополнительные BIN, неполную factory-тройку или символические ссылки.
- Пакет предназначен для другого семейства ESP32.
- Таблица разделов или OTA-метаданные повреждены.
- Таблица разделов находится по нестандартному адресу, который не удаётся обнаружить ограниченным сканированием.
- Образ не помещается в целевой раздел.
- Питание отключено до или после переключения OTA-слота.
- Необязательный UART-маркер разбит между несколькими порциями данных или не появился до таймаута.
- Каталог рядом с EXE недоступен для записи.
- Пользователь пытается закрыть приложение во время критической записи.
- Пользователь отключает монитор вручную, меняет baud или COM-порт.
- Поток UART не освобождает COM-порт до таймаута начала прошивки.

## Функциональные требования

- **REQ-001**: Система должна поставляться как один portable EXE для Windows 10/11 x64 и работать без Python, внешнего прошивальщика и установки приложения.
- **REQ-002**: Система должна предоставлять клиентский и производственный режимы в одном EXE; клиентский режим открывается по умолчанию.
- **REQ-003**: Система должна неинвазивно обнаруживать появление COM-портов и автоматически выбирать единственный порт, не открывая его и не переключая DTR/RTS до явного запуска операции; при нескольких портах требуется ручной выбор, а чип ESP32 определяется внутри запущенной операции.
- **REQ-004**: Система должна принимать без обязательного манифеста: для factory — папку `bootloader.bin` + `partitions.bin` + `firmware.bin` с необязательным `boot_app0.bin`; для update — выбранный пользователем application `.bin` с любым именем.
- **REQ-005**: Производственный режим должен записывать произвольное количество сегментов пакета на фиксированной максимальной скорости и запускать каждый цикл только по кнопке.
- **REQ-006**: Клиентский режим должен обновлять одним BIN как factory-only, так и OTA-разметку.
- **REQ-007**: OTA-обновление должно сначала записывать и проверять неактивный слот и только затем атомарно переключать загрузку через `otadata`; при отсутствии безопасного слота требуется явное подтверждение in-place записи.
- **REQ-008**: Пользователь должен видеть стадии, процент, диагностический лог и автоматически открытый UART-монитор; UART-чанки должны склеиваться без искусственных переводов строки, а длинные строки не должны автоматически переноситься.
- **REQ-009**: UART-маркер готовности должен быть необязательной настройкой; при его отсутствии результат записи определяется flash verify, а монитор всё равно открывается автоматически.
- **REQ-010**: До записи система должна проверить формат ESP image, целевой чип, таблицу разделов, размеры, адреса, пересечения и вместимость flash/раздела.
- **REQ-011**: Производственный режим должен вести сессионные счётчики и UTF-8 CSV-отчёт по каждой плате.
- **REQ-012**: Настройки, диагностические логи и отчёты должны по умолчанию храниться рядом с EXE; при невозможности записи пользователь выбирает рабочую папку.
- **REQ-013**: Полное стирание должно быть отдельной подтверждаемой опцией только производственного режима и по умолчанию быть выключено.
- **REQ-014**: Отдельный инструмент подготовки версионированных пакетов должен сохраняться как необязательный advanced workflow и обратная совместимость.
- **REQ-015**: Любая ошибка должна иметь стабильный код, понятное сообщение, запись в лог и не должна приводить к ложному успешному результату.
- **REQ-016**: Система не должна выполнять скрытый переход на меньшую скорость прошивки, сетевую загрузку прошивок или отправку телеметрии.
- **REQ-017**: Для factory-папки система должна разбирать `partitions.bin`, получать application/otadata offsets и определять bootloader offset по семейству ESP32; неоднозначные карты должны блокироваться.
- **REQ-018**: Для одиночного application BIN система должна читать и валидировать partition table и `otadata` с подключённой платы до любой записи.
- **REQ-019**: При update система должна выбирать неактивный OTA-слот, а не фиксированный `ota_0`; если устройство загружено из factory и доступен `ota_0`, он считается безопасной целью.
- **REQ-020**: `firmware.json` должен поддерживаться только как необязательный legacy-формат и не упоминаться как обязательный шаг основного UX.
- **REQ-021**: Пользователь до factory flash должен видеть источник распознавания, число BIN, целевой чип и вычисленную карту адресов.
- **REQ-022**: UART-монитор должен работать независимо от прошивки: первый вход на вкладку пассивно открывает выбранный порт, ручное отключение требует явного повторного подключения, baud выбирается и сохраняется, обычный reset доступен только при подключении; flash должен атомарно забрать COM-порт с ограниченным ожиданием, заблокировать UART UI и после завершения восстановить монитор.
- **REQ-023**: Приложение должно получать пользовательский locale Windows при
  запуске, выбирать русский интерфейс только для `ru-*` и английский для всех
  остальных значений и fallback-сценариев.
- **REQ-024**: Все пользовательские подписи, диалоги, статусы, ошибки и стадии
  должны иметь русскую и английскую формулировку; английский режим не должен
  показывать русские диагностические сообщения.
- **REQ-025**: Публичное имя продукта должно быть `ESP32 Flasher`; portable EXE,
  окно, metadata, README, Pages и release assets должны использовать это имя.
- **REQ-026**: Публичный репозиторий `tigramaan/esp32-flasher` должен содержать
  английские README и release notes, MIT License, reproducible Windows workflow
  и downloadable portable x64 EXE с SHA-256.
- **REQ-027**: GitHub Pages должен быть англоязычным, responsive и доступным,
  содержать canonical/description/Open Graph metadata, SoftwareApplication и
  FAQ structured data, `robots.txt`, `sitemap.xml`, `llms.txt`, фактическое
  описание возможностей и ссылку на latest release без неподтверждённых claims.

## Ключевые сущности

- **FirmwareSelection**: выбранная factory-папка или update BIN, распознанный формат, назначение, целевой чип и набор сегментов.
- **FirmwareSegment**: роль, относительный путь, размер, вычисленный хэш и, для первичной прошивки, адрес.
- **DetectedDevice**: COM-порт, аппаратный идентификатор, семейство чипа, MAC и состояние доступности.
- **FlashOperation**: одна конечная операция с идентификатором, стадиями, прогрессом и результатом.
- **FactorySession**: набор последовательных операций, счётчики и неизменяемый отчёт.

## Критерии успеха

- **SC-001**: Пользователь выполняет обычное обновление, совершив не более трёх действий после запуска: выбрать BIN-файл, подключить устройство, нажать кнопку.
- **SC-002**: В 100% тестов повреждённые или несовместимые пакеты блокируются до первого изменения flash.
- **SC-003**: После отключения платы производственный экран готов к следующему циклу не позднее чем через две секунды.
- **SC-004**: Для 100% завершённых производственных циклов существует ровно одна строка отчёта с однозначным результатом.
- **SC-005**: При OTA-сбое до переключения загрузки устройство сохраняет ранее активный образ.
- **SC-006**: Во время записи и потока UART не менее 1 Мбит/с визуальный статус обновляется не реже одного раза в 250 мс, а окно не получает состояние Windows «Не отвечает».
- **SC-007**: EXE запускается на чистых поддерживаемых Windows без среды разработки и интерпретаторов.
- **SC-008**: Direct UART подключается или возвращает явную ошибку не позднее двух секунд; начало flash никогда не пересекается с потоком монитора, удерживающим тот же COM-порт.
- **SC-009**: Для `ru-RU`, `en-US` и минимум одного другого locale 100%
  пользовательских элементов отображаются на ожидаемом языке.
- **SC-010**: Latest release содержит запускаемый portable Windows x64 EXE и
  SHA-256; ссылки README и Pages ведут на этот релиз без ручного изменения версии.
- **SC-011**: Pages не имеет горизонтального overflow и критических ошибок на
  smoke-матрице 320–3840 CSS px, а поисковые и structured-data артефакты
  проходят автоматическую проверку структуры.

## Предположения и границы

- Одновременно обслуживается одна плата; параллельная прошивка несколькими портами не входит в v1.
- Интерфейс v1 русскоязычный для `ru-*` Windows locale и англоязычный во всех
  остальных случаях; тема следует системной светлой/тёмной теме.
- Скорость записи фиксирована на `921600`; плохой кабель считается ошибкой, автоматического fallback нет.
- USB-UART драйвер и системный WebView2 уже присутствуют в Windows.
- Для прямой папки rollback-политика не выводится надёжно из BIN и по умолчанию не включается; legacy manifest может явно включить её.
- Вычисленный при загрузке SHA-256 используется для диагностики и защиты от изменения файла между стадиями, но не доказывает автора прошивки.
- Автоматическое обновление EXE, сетевой каталог прошивок, подпись пакетов и сравнение с текущей версией устройства не входят в v1.
